# Persistence: entities, repositories, queries

Schema is generated by Hibernate (`ddl-auto=update`); there is no Flyway/Liquibase. Anything JPA can't express is applied by hand.

## BaseEntity

All entities (except `TmdbMovie`) extend `BaseEntity`:

- `id` (Long) — DB primary key, `@GeneratedValue(IDENTITY)`
- `uuid` (String) — API-facing identifier, generated in `@PrePersist`
- `version` (long) — optimistic locking via `@Version`
- `createdAt`, `updatedAt` — JPA auditing timestamps (`Instant`, see [Timestamps](#timestamps))
- `@Audited` — Hibernate Envers. The annotation is declared on `BaseEntity` only; subclasses aren't annotated. Config: `store_data_at_delete=true`, `global_with_modified_flag=true`, modified-flag columns suffixed `_MODIFIED`

**`id` vs `uuid` for lookups:** use `uuid` only when the identifier comes from outside the server (path variables, request bodies). Once you have an entity, pass its `id` to repository/service helpers — a `uuid` lookup there is a pointless string-indexed query.

## BaseRepository

All repositories extend `BaseRepository<T extends BaseEntity>` (`JpaRepository<T, Long>` + a `default T findOne(Long id)`).

`TmdbMovieRepository` is the exception: `TmdbMovie` uses its TMDB id as the primary key (no UUID, no audit columns, no `BaseEntity`), so it extends `JpaRepository<TmdbMovie, Long>` directly.

## Avoiding N+1

- `HallRepository.findByUuidWithType` and `findAllFiltered` (an **unpaged** `List<Hall>` filtered by `excludeHallId` / `statuses`) `JOIN FETCH h.type`. Apply the same pattern to new finders that need the type.
- `Hall.layout` and `Hall.categoryPrices` are JSONB columns loaded with the row — nothing else to fetch.
- The `/backend-rules` command (`cinefy-backend/.claude/commands/backend-rules.md`) has the general `@EntityGraph` / `JOIN FETCH` rules, including the paginated-collection trap.

## `@Query` strings aren't checked by `mvn compile`

They are parsed at bean-creation time, so a broken JPQL expression compiles fine and fails at startup. Boot the app (or generate its SQL) after adding or reshaping a query. Traps met in practice:

- `MAX(...)` returns `Integer`, so projecting into a `boolean` record component needs `MAX(...) > 0` in the query. A type mismatch surfaces as the unhelpful `Missing constructor for type '...'`.
- Hibernate expands `GROUP BY <entity>` to the primary key alone. That's what keeps JSONB columns out of the `GROUP BY` — e.g. `TmdbMovie.credits` in the `GROUP BY m` queries of `TmdbMovieRepository` — since Postgres has no equality operator for `jsonb` and would otherwise reject the query.

## Entity conventions

- **Code field:** entities with user-facing names (`Hall`, `HallType`, `PaymentGateway`) derive a `code` via a static `toCode(String name)` (trimmed, lowercased, spaces → underscores). Used for uniqueness checks: `existsByCode` / `existsByCodeAndIdNot`, or the `…AndDeletedAtIsNull` variants for `PaymentGateway`.
- **Relationships:** `CascadeType.ALL` + `orphanRemoval = true` on parent-owned collections (e.g. `Booking.seats`); `FetchType.LAZY` on all `@ManyToOne`; association collections are `Set`, not `List`. JSONB-mapped data (`Hall.layout`, `Hall.categoryPrices`) is the exception — those are serialized columns, not associations.
- **Enums** parsed from API input expose a static `fromString(String)` — use it instead of `valueOf` so bad values raise `BusinessException` consistently. Internal-only enums (e.g. `UserType`) are bare.

## Naming strategy

`CinefyTableNamingStrategy` maps entity names → `UPPER_PLURAL` tables and camelCase fields → `UPPER_SNAKE_CASE` columns. Envers audit tables use the `_REVISIONS` suffix with `REVISION_ID` / `REVISION_TYPE` columns.

## Timestamps

A point in time is an `Instant` mapped to `TIMESTAMPTZ(0)`: `BaseEntity.createdAt` / `updatedAt`, `Booking.expiresAt`, `InvalidJwt.expirationDate`, `PaymentGateway.deletedAt`, `Showtime.startDateTime` / `endDateTime`, and `TmdbMovie.lastSyncedAt`. "Now" is `Instant.now()`, and repository parameters compared against these columns are `Instant` (a nullable one is null-checked with `CAST(:x AS Instant)`). **`Instant` stays internal.** Display fields in response DTOs are `LocalDateTime`s holding cinema wall time with no offset (`"2026-10-09T20:00:00"`), mapped with `DateUtil.toCinemaDateTime`: `startDateTime` in the booking DTOs, `SeatSelectionDTO` and `ShowtimeSummaryDTO`, `PaymentGatewaySummaryDTO.createdAt`, `StaffMemberDetailDTO.hiredAt`. Without an offset, the browser shows the wall time as given, so every viewer sees cinema time. The exception is `expiresAt` (`ActiveBookingDTO`, `BookingDetailDTO`, `BookingSummaryDTO`), which stays an `Instant` (`…Z`): it drives countdowns, which need an absolute moment. A new display field follows the same split: a time to show is a cinema `LocalDateTime`, a moment to count down to or compare with "now" in the browser is an `Instant`. The one input, `ShowtimeDTO.dateTime`, is a `LocalDateTime` holding cinema wall time (`'2026-04-25T19:30:00'`) that `DateUtil.toInstant` converts, so DST is resolved on the server.

A **calendar day** belongs to the cinema, not to the server or the viewer. **All zone handling goes through the `DateUtil` bean** (`utils/`, zone from `app.cinema-time-zone`); no other class touches a `ZoneId`. It turns a `LocalDate` into a range (`startOfDay(date)` up to `startOfDay(date.plusDays(1))`, or `endOfDay` for the statistics `BETWEEN`), and provides "today" (`today()`), cinema wall-clock "now" for the staff on-shift check (`now()`), `toCinemaDate` / `toCinemaDateTime` for responses and the ticket email's `showtimeStart`, and `formatTime` for the `HH:mm` strings in `MovieShowtimeListItemDTO.time`, `ScheduledShowtimeDTO.startsAt` / `endsAt` and `BookingShowtimeDTO`. Never call `LocalDate.now()` / `LocalDateTime.now()` without it: those use the JVM zone (UTC in prod). **Queries never turn a timestamp into a date.** `CAST(... AS LocalDate)` would use the Postgres session zone (the JVM's, UTC in prod), not the cinema's. Day-shaped results are built in Java instead: `findStartDateTimesByMovieAndStatuses` / `findBookableStartDateTimes` return start instants that the services map to distinct cinema dates, and the daily statistics queries return rows keyed by start instant that `StatisticsService` buckets with `DateUtil.toCinemaDate`. A new day-based query follows the same pattern: SQL compares instants, Java converts with `DateUtil`.

## Where a domain predicate lives

Put it on the entity when the entity holds every value it needs — `Booking.hasExpired()` compares its own `expiresAt`. Put it with the policy owner when an external threshold is involved: bookability depends on `BOOKING_CUTOFF_MINUTES`, which is booking policy, so it's `BookingService.isBookable(Showtime)` (`public static`), not a `Showtime` method taking a cutoff parameter.

`ShowtimeService` calls `BookingService.isBookable(showtime)` when mapping `bookable` onto `MovieShowtimeListItemDTO` / `ShowtimeSummaryDTO`. The same rule is **also** in SQL (`findBookableStartDateTimes`, `findBookableByMovieAndDateRangeWithHall` take a `cutOffDate`) — change both together.

## DTOs

- **Input DTOs** use Jakarta Validation (`@NotBlank`, `@NotNull`, `@Min`, `@Valid`); business rules beyond annotations are validated procedurally in services.
- **Output DTOs** are per use case: `*SummaryDTO` (lists), `*DetailDTO` (full entity), `*LayoutDTO` (domain projections).
- **Class vs record:** a Lombok `@Getter`/`@Setter` class when Jackson deserializes it (request bodies), it carries Bean Validation, or a service mapper fills it with setters. A `record` for small immutable read-only results built in one shot (`CurrentStaffMemberDTO`, `TokenPairDTO`, projections).
